Framework

評価フレームワーク

各方向性を4段階で検証する。課題の実在性から始め、市場適合性まで順に確認する。

CPF

Customer-Problem Fit

顧客と課題の整合性。課題は本当に存在するか

PSF

Problem-Solution Fit

課題と解決策の整合性。解決策は刺さるか

SPF

Solution-Product Fit

解決策とプロダクトの整合性。技術的に実現可能か

PMF

Product-Market Fit

プロダクトと市場の整合性。持続的に収益化できるか

Direction 01
①
デジタルショップカード
コーヒー屋の名刺・ショップカードをQRページに置き換える
顧客課題深刻度
コーヒー屋（店主）ショップカードの印刷コスト・在庫管理・情報更新の手間★★★
コーヒー屋（店主）豆を買ったお客さんへの「淹れ方」フォローができない★★★★
エンドユーザーもらったショップカードを使わない・失くす★★★
エンドユーザー買った豆の最適な淹れ方が分からない★★★★
PSF — 解決策
  • QRコード → ショップページ（レシピ＋SNS＋オンラインストアリンク）
  • ショップページはコーヒー屋が自分で編集可能
  • 印刷コスト0・常に最新情報・購買後の体験継続
  • エンドユーザーはアプリ不要で閲覧できる
SPF — 実装方針
  • 既存レシピ機能を流用（技術的ギャップ：中）
  • 追加: ショップページテンプレート・QR生成・外部リンク管理
  • 公開URL brew.com/s/:handle は認証不要
  • 管理画面 brew.com/shop は別ロールで分離
PMF — 市場・収益
  • 市場：国内個人・小規模スペシャルティコーヒーショップ（推定 5,000〜10,000店）
  • 競合：Linktree（汎用）・食べログ（重い）→ コーヒー特化の空白
  • Free：ショップページ1枚・レシピ3件
  • Pro（月額1,500〜3,000円）：無制限・QR・アナリティクス
初期獲得戦略
  • 無料QR生成ツールとして拡散
  • コーヒー屋がSNSでQRページをシェア → エンドユーザー流入
  • エンドユーザーがレシピを試す → Proへの転換需要
  • B2B（店舗）とB2C（個人）が同時に獲得できる
優先度：最高 — 開発コストが最も低く、B2BとB2Cの流入が同時に成立する。既存の「レシピプラットフォーム」のドメインパワーを直接活かせる唯一の方向性。
Direction 02
②
QR × レシピ共有モデル
店舗が自分のやり方でQRとレシピを紐づけられる柔軟な仕組み
顧客課題深刻度
コーヒー屋全般買った豆の淹れ方をお客さんに伝える手段がない★★★★
エンドユーザー高い豆を買ったのに美味しく淹れられない★★★★
ロースター豆の説明を紙で書くのに限界（文字数・更新できない）★★★

「豆ごとにQRを貼る」は非現実的な場合が多い。店舗によってレシピの粒度は大きく異なる。

ユースケース具体例QRの単位
定番レシピ型「うちの抽出はこれ一択」のこだわり店店舗QR 1枚
焙煎度別型ライト・ミディアム・ダークで湯温・時間が異なる焙煎度別 × 3枚

PSF — 解決策
  • 店舗が「QRページ」を作成し、紐づけるレシピを自由に選択・構成
  • リンク先は「一覧」「単一レシピ」「焙煎度セレクタ」のいずれも選択可
  • 最小構成：1枚のQRを代表レシピに飛ばすだけで即使える
PMF — 収益モデル
  • 市場：国内マイクロロースター〜小規模カフェ（推定 5,000〜15,000店）
  • Free：QRページ1枚・レシピ3件
  • Pro（月額1,500〜3,000円）：複数QR・テンプレート選択・アナリティクス
方向性①と統合可能 — ショップカード機能の「レシピ紐づけ方法」として②の柔軟な設計をそのまま採用できる。別機能ではなく、①のサブ機能として設計するのが最も効率的。

③
バリスタ間レシピ共有プラットフォーム
プロバリスタが使えるレシピ共有・チーム管理ツール
顧客課題深刻度
バリスタ（プロ）レシピをNotion/スプレッドシートで管理しており統一感がない★★
カフェオーナースタッフ間のレシピ標準化ができていない★★★
バリスタ（プロ）プロ向けパラメータ（TDS・収率・EY）が一般レシピには不足★★★★
PSF — 解決策
  • プロモード：TDS・EY・水温・タンピング圧などの詳細パラメータ
  • チーム機能：店舗ごとのレシピライブラリ・閲覧権限管理
  • バージョン管理：レシピの改訂履歴
PMF — 収益モデル
  • 市場規模：小さいがLTVが高い（店舗契約）
  • チームプラン（月額5,000〜10,000円/店舗）
  • 競合：Notion・専用POSシステム → コーヒー特化の空白あり
現状のレシピ粒度はホームユーザー向けで、プロには不十分。ただし機能追加で解決できる（プロモードの追加）。技術的ギャップは大きく、B2Bサービスとしての設計が必要なため中期以降の優先度とする。

⑤
美容室型・コーヒーカルテ
ユーザーの購入・抽出履歴を蓄積し、次回来店時に最適な提案を可能にする
顧客課題深刻度
バリスタ常連客の好みを記憶・管理するツールがない★★★
エンドユーザー飲んだ豆の記録が残らず、好みの傾向が見えない★★★
エンドユーザー「おすすめ教えて」と毎回一から説明するのが面倒★★★★
美容室との類比

美容師は「前回のカット・髪質・ライフスタイル」をカルテで把握し次回提案できる。コーヒーも「前回の豆（産地・焙煎度）・好みのフレーバー・器具」が蓄積できれば「今回はエチオピア飲んでたからケニアどうですか」と自然に提案できる。

段階的な実装アプローチ
  1. ユーザーが「飲んだ豆メモ」を記録する機能（最小MVP）
  2. QRチェックインで店舗連携
  3. バリスタ向け閲覧UI（カルテ機能）
収益モデルは店舗が顧客CRMとして月額契約（3,000〜8,000円/店舗）。ユーザー側は無料。美容室モデルと同じ構造で、LTV・解約率ともに有利な設計になる。
Architecture Decision

「同一サービスか分離か」
アーキテクチャ判断

ショップカード機能を既存レシピプラットフォームに統合すべきかどうかの分析。

Option A — 却下

完全に別サービスとして分離

shop.brew.com と brew.com を完全に独立したアプリケーションとして構築する。

  • 「レシピ共有」のドメインパワーをショップページが活かせない
  • レシピデータの同期にAPIブリッジが必要（運用複雑化）
  • 初期フェーズで2サービス並行運用はコストが高すぎる
Option B — 推奨

同一コードベース × 別プロダクト面

1つのリポジトリで管理し、URLとロールでコンシューマーとショップを分離する。

  • レシピDBは完全共有（ショップページはレシピを「参照」するだけ）
  • コンシューマーUXとショップ管理UIは完全に分離
  • エンドユーザーはショップ管理画面の存在を知る必要がない
  • 将来の完全分離も可能（モジュール境界を維持する設計を選ぶ）
    • brew.com/ ← 個人ユーザー向けレシピプラットフォーム（ネット流入・SEO） brew.com/shop/ ← ショップオーナー向け管理画面（別ロール・別オンボーディング） brew.com/s/:handle ← 公開ショップページ（認証不要・QRからの着地点） ┌─────────────────────────────────────────────┐ │ Shared Backend │ │ recipes DB ← 参照のみ → shop pages DB │ │ user auth shop owner auth │ └─────────────────────────────────────────────┘
    レイヤー共有するか理由
    レシピデータ共有ショップページはレシピを参照するだけ。別DBにするとデータ同期地獄
    認証・アカウント分離個人（軽量）とショップオーナー（法人・決済・権限管理）は要件が全く異なる
    UI / UX分離消費者の探索体験とB2B管理ツールを混ぜると両方が中途半端になる
    コードベース統合初期は1リポジトリが保守コスト最小。将来の分離に備えモジュール境界を維持
